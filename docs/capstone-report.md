## บทคัดย่อ

โครงงานโปรแกรมประยุกต์บนเว็บสำหรับการตรวจสอบการออกแบบอาคารเพื่อการเข้าถึง เป็นระบบแพลตฟอร์มเว็บแอปพลิเคชันที่พัฒนาขึ้นเพื่อช่วยผู้ตรวจสอบในการประเมินอาคารและสิ่งปลูกสร้างตามมาตรฐาน **มยผ. 6301** เรื่อง การออกแบบอาคารและสิ่งปลูกสร้างเพื่อการเข้าถึงและการใช้ประโยชน์อย่างเท่าเทียมสำหรับคนพิการและผู้สูงอายุ ซึ่งเป็นมาตรฐานของภาครัฐไทยด้านการออกแบบที่ครอบคลุม

ปัจจุบันการตรวจสอบตามมาตรฐานดังกล่าวมักดำเนินการด้วยเอกสารกระดาษหรือสเปรดชีต ทำให้ข้อมูลกระจัดกระจาย ยากต่อการติดตามความคืบหน้า และไม่สะดวกในการบันทึกภาพถ่ายหลักฐานการตรวจในสถานที่จริง โครงงานนี้จึงพัฒนาระบบเว็บแอปพลิเคชันแบบ **Mobile-first** ที่ผู้ใช้สามารถลงทะเบียน เข้าสู่ระบบ สร้างโครงการตรวจ (อาคาร/สถานที่) เลือกกลุ่มเกณฑ์ที่ต้องการประเมิน ให้คะแนนแต่ละข้อ (0 / 1 / 2) บันทึกหมายเหตุ อัปโหลดภาพถ่ายการตรวจ และดู **ภาพอ้างอิง** จากมาตรฐานอย่างเป็นทางการได้ในที่เดียว ระบบยังรองรับการทำงานร่วมกันหลายผู้ตรวจผ่านลิงก์เชิญ และคำนวณ **เปอร์เซ็นต์ความสมบูรณ์** ของแต่ละโครงการอัตโนมัติ

ฟังก์ชันหลักของระบบประกอบด้วย ระบบจัดการบัญชีผู้ใช้พร้อมยืนยันอีเมลด้วย OTP แดชบอร์ดโครงการตรวจพร้อมการค้นหา หน้าตรวจรายการเกณฑ์ตามมาตรฐาน การอัปโหลดภาพผ่าน UploadThing ระบบแชร์โครงการให้ทีมตรวจร่วมกัน และชุดข้อมูลมาตรฐาน 8 หมวดในรูปแบบ JSON พร้อมภาพอ้างอิง 71 ภาพที่สกัดจาก PDF มาตรฐาน โดยเว็บแอปพลิเคชันนี้นำความรู้จากรายวิชาการเขียนโปรแกรมเว็บ ระบบฐานข้อมูล และการพัฒนาแอปพลิเคชันมาประยุกต์ใช้กับโครงการนี้

**คำสำคัญ:** โปรแกรมประยุกต์เว็บไซต์, มยผ. 6301, การออกแบบเพื่อการเข้าถึง, การตรวจสอบอาคาร, MongoDB

## Abstract

The Web Application for Building Accessibility Inspection is a mobile-first web platform developed to assist inspectors in evaluating buildings and facilities against Thai public-sector standard **มยผ. 6301** (Inclusive Design for People with Disabilities and Older Adults). Currently, compliance inspections are often conducted using paper forms or spreadsheets, resulting in scattered data, difficulty tracking progress, and inconvenience when capturing on-site photographic evidence.

This project addresses these issues by developing a web application where users can register, log in, create inspection projects (sites/buildings), select criteria groups, score each criterion (0 / 1 / 2), add notes, upload inspection photos, and view official **reference figures** from the standard—all in one place. The system supports multi-inspector collaboration via invite links and automatically calculates **completion percentage** per project.

Core functions include user account management with OTP email verification, a project dashboard with search, criteria checklist pages aligned with the standard, image uploads via UploadThing, project sharing for team inspections, and a standards catalog of 8 sections in JSON format with 71 reference images extracted from the official PDF. The application integrates knowledge from Web Programming, Database Systems, and Application Development courses.

**Keywords:** Web Application, มยผ. 6301, Accessibility Design, Building Inspection, MongoDB

## 1. บทนำ

### 1.1 ที่มา และความสำคัญ

การออกแบบอาคารและสิ่งปลูกสร้างให้ผู้พิการและผู้สูงอายุเข้าถึงและใช้ประโยชน์ได้อย่างเท่าเทียม เป็นหัวใจสำคัญของการพัฒนาเมืองและบริการสาธารณะที่ครอบคลุม ในประเทศไทย กรมโยธาธิการและผังเมืองกำหนดมาตรฐาน **มยผ. 6301** เป็นแนวทางการออกแบบที่ครอบคลุมหลายด้าน เช่น ทางเข้าอาคาร ทางลาด ลิฟต์ บันได ประตูและหน้าต่าง ที่จอดรถ ป้ายสัญลักษณ์ และสิ่งอำนวยความสะดวกต่าง ๆ

อย่างไรก็ตาม การนำมาตรฐานไปใช้ในทางปฏิบัติ โดยเฉพาะการตรวจประเมินในสถานที่จริง มักพบปัญหาดังนี้

- เอกสารมาตรฐานมีข้อกำหนดจำนวนมาก ทำให้การค้นหาและอ้างอิงในระหว่างตรวจลำบาก
- การบันทึกผลด้วยกระดาษหรือไฟล์แยกส่วน ทำให้ข้อมูลไม่เป็นหนึ่งเดียวและติดตามความคืบหน้ายาก
- การเก็บภาพถ่ายหลักฐานและภาพอ้างอิงจากมาตรฐาน ต้องสลับระหว่างเอกสาร PDF กับอุปกรณ์ถ่ายภาพ
- เมื่อมีผู้ตรวจหลายคนในทีม การแบ่งงานและรวมผลอาจเกิดความซ้ำซ้อนหรือข้อมูลขัดแย้ง

ดังนั้น คณะผู้จัดทำจึงพัฒนา **โปรแกรมประยุกต์บนเว็บสำหรับการตรวจสอบการออกแบบอาคารเพื่อการเข้าถึง** ขึ้น เพื่อให้ผู้ตรวจสามารถทำงานบนมือถือหรือแท็บเล็ตในสนาม บันทึกคะแนน หมายเหตุ และภาพถ่ายได้ทันที พร้อมดูภาพอ้างอิงจากมาตรฐานและติดตามความคืบหน้าของโครงการได้อย่างเป็นระบบ

### 1.2 วัตถุประสงค์

1. เพื่อพัฒนาโปรแกรมประยุกต์บนเว็บสำหรับการตรวจสอบอาคารตามมาตรฐาน มยผ. 6301

### 1.3 ทฤษฎี และวรรณกรรมที่เกี่ยวข้อง

#### 1.3.1 การออกแบบเพื่อการเข้าถึง (Universal / Inclusive Design)

การออกแบบเพื่อการเข้าถึง (Accessible Design) หมายถึงการออกแบบสิ่งแวดล้อม ผลิตภัณฑ์ และบริการให้ผู้คนหลากหลายกลุ่ม รวมถึงผู้พิการและผู้สูงอายุ สามารถใช้งานได้อย่างปลอดภัยและมีประสิทธิภาพ [1] มาตรฐาน มยผ. 6301 ของไทยจัดทำขึ้นเพื่อเป็นแนวทางเชิงปฏิบัติสำหรับหน่วยงานภาครัฐและผู้เกี่ยวข้องในการออกแบบและตรวจสอบอาคาร

#### 1.3.2 โปรแกรมประยุกต์บนเว็บ (Web Application)

โปรแกรมประยุกต์บนเว็บ คือซอฟต์แวร์ที่ผู้ใช้เข้าถึงผ่านเว็บเบราว์เซอร์โดยไม่ต้องติดตั้งลงเครื่อง ทำให้ใช้งานได้ทุกที่และทุกอุปกรณ์ [2] ระบบแบ่งเป็น 2 ส่วนหลัก ได้แก่ ส่วนติดต่อผู้ใช้ (Front-End) และส่วนเซิร์ฟเวอร์ (Back-End) ซึ่งสื่อสารกันผ่าน RESTful API

#### 1.3.3 เครื่องมือและเทคโนโลยีที่ใช้พัฒนา

**ส่วนติดต่อผู้ใช้**

1. **Next.js** — เฟรมเวิร์กของ React ที่รองรับ App Router, Server Components และ API Routes ช่วยให้พัฒนาเว็บแอปพลิเคชันที่มีประสิทธิภาพและโหลดเร็ว [3]
2. **React** — ไลบรารี JavaScript สำหรับสร้าง UI แบบ component-based ช่วยจัดการ state และการแสดงผลแบบ dynamic [4]
3. **CSS Modules** — วิธีจัดการสไตล์แบบ scoped ลดการชนกันของ class ในโปรเจกต์ขนาดใหญ่
4. **TypeScript** — ภาษาที่เพิ่ม type safety บน JavaScript ช่วยลดข้อผิดพลาดระหว่างพัฒนา [5]

**ส่วนเซิร์ฟเวอร์และฐานข้อมูล**

5. **Node.js** — สภาพแวดล้อมรัน JavaScript ฝั่งเซิร์ฟเวอร์ รองรับการทำงานแบบ asynchronous [6]
6. **MongoDB** — ฐานข้อมูล NoSQL แบบ document ยืดหยุ่น เหมาะกับโครงสร้างข้อมูลโครงการตรวจที่มี sections และ criteria ซ้อนกัน [7]
7. **Mongoose** — ODM สำหรับ MongoDB ช่วยกำหนด schema, validation และ middleware (เช่น คำนวณ completion rate ก่อนบันทึก)
8. **NextAuth (Auth.js)** — ไลบรารี authentication รองรับ Credentials provider และ JWT session [8]
9. **UploadThing** — บริการอัปโหลดไฟล์สำหรับรูปโปรไฟล์ รูปปกโครงการ และรูปการตรวจ [9]
10. **bcryptjs** — ใช้เข้ารหัสรหัสผ่านผู้ใช้ก่อนจัดเก็บในฐานข้อมูล

**เครื่องมือเสริม**

11. **Python + PyMuPDF** — ใช้สกัดภาพอ้างอิงจาก PDF มาตรฐาน มยผ. 6301 ในระหว่างขั้นตอน build (ไม่ใช้ runtime)
12. **Visual Studio Code / Cursor** — เครื่องมือพัฒนาและควบคุมเวอร์ชันด้วย Git / GitHub

2. ลดเวลาในการค้นหาและอ้างอิงข้อความ/ภาพจากมาตรฐาน มยผ. 6301
3. ติดตามความคืบหน้าการตรวจแต่ละโครงการผ่านเปอร์เซ็นต์ความสมบูรณ์
4. ทีมตรวจหลายคนสามารถทำงานร่วมกันบนโครงการเดียวกันผ่านลิงก์เชิญ
5. ข้อมูลการตรวจ หมายเหตุ และภาพถ่าย อยู่ในที่เดียว พร้อมสำหรับการทบทวนหรือรายงานต่อไป

## 2. วิธีการดำเนินโครงงาน

### 2.1 การรวบรวมและจัดทำข้อมูลมาตรฐาน (Data Collection)

ในการจัดทำโครงงานมีการใช้เอกสารมาตรฐาน **มยผ. 6301** ฉบับที่กรมโยธาธิการและผังเมืองกำหนด เป็นแหล่งอ้างอิงหลัก โดยแปลงข้อกำหนดเป็นไฟล์ JSON 8 ชุด เก็บใน `lib/standards/` แต่ละรายการมี `item_id`, `display_text`, `source_text`, `notes` และการอ้างอิงภาพ

สำหรับภาพอ้างอิง (reference figures) ใช้สคริปต์ Python `scripts/extract-pdf-figures.py` สกัดจาก PDF ต้นฉบับ (`standards-source/maypho6301.pdf`) ได้ภาพ PNG 71 ไฟล์ใน `public/standards/figures/` และ metadata ใน `lib/standards/figure-map.json` เพื่อเชื่อม `source_clause` กับไฟล์ภาพที่ถูกต้อง

### 2.2 การออกแบบฐานข้อมูล (Database Design)

ระบบใช้ **MongoDB** ผ่าน **Mongoose** โดยมี entity หลัก 2 ชนิด

**User**

- `firstName`, `lastName`, `password` (hash ด้วย bcrypt)
- `contact.email` — ใช้ login, unique
- `profileImg` — URL จาก UploadThing
- `organization` (optional)

**Project**

- `userId` — เจ้าของโครงการ (ไม่โอนสิทธิ์)
- `members[]` — ผู้ร่วมตรวจ role `editor` ที่ join ผ่าน token
- `projectName`, `description`, `institution.address`, `coverImg`, `status`
- `sections[]` → `selectedGroups` → `criteria[]`
- แต่ละ criterion: `criteriaId`, `score` (0|1|2|null), `note`, `imgs[]`, `updatedAt`
- Pre-save hook คำนวณ `completionRate` ของ section และ project

> **หมายเหตุ:** แทรก ER Diagram หรือแผนภาพความสัมพันธ์ (รูปที่ 1) — ออกแบบด้วย Lucidchart หรือเครื่องมือที่ทีมใช้

### 2.3 การออกแบบส่วนต่อประสานกับผู้ใช้ (UI/UX Design)

ออกแบบให้เป็น **Mobile-first** ด้วยคอมโพเนนต์ `PhoneShell` (ความกว้างสูงสุด ~420px) เพื่อจำลองประสบการณ์แอปบนมือถือ เหมาะกับการตรวจในสนาม ใช้โทนสี teal gradient สอดคล้องกับธีมการตรวจ/ความน่าเชื่อถือ

หน้าหลักที่ออกแบบ ได้แก่ Login, Register (พร้อม OTP), Profile, แดชบอร์ดโครงการ, สร้างโครงการ, เลือก section, รายการเกณฑ์ (InspectionItemRow), และ modal แชร์โครงการ

> **หมายเหตุ:** แทรกภาพ mockup จาก Figma (รูปที่ 2) หากมี

### 2.4 การพัฒนาเว็บแอปพลิเคชัน (Website Development)

#### 2.4.1 ฝั่ง Front-End

- **Next.js 16** (App Router) + **React 19**
- หน้า client component สำหรับ auth, upload, และการตรวจ (`"use client"` pattern ตาม convention ของโปรเจกต์)
- CSS Modules ใน `app/allproject/_components/*.module.css`

#### 2.4.2 ฝั่ง Back-End (API Routes)

API หลักใน `app/api/`:

| Method | Endpoint | คำอธิบาย |
|--------|----------|----------|
| GET/POST | `/api/project` | รายการโครงการ (ของตน + ที่ share) / สร้างโครงการ |
| GET/PATCH/DELETE | `/api/project/[projectId]` | ดู / แก้ไข / ลบโครงการ |
| PATCH | `/api/project/[projectId]/critiria/[critiriaId]` | อัปเดตคะแนน หมายเหตุ รูป (รองรับ conflict 409) |
| POST | `/api/project/[projectId]/collaboration` | เปิด/ปิด/rotate invite |
| POST | `/api/join/[token]` | รับคำเชิญเข้าทีม |
| POST | `/api/auth/register` | ลงทะเบียน |
| POST | `/api/uploadthing` | อัปโหลดรูป |

Authentication ใช้ **NextAuth v5** แบบ Credentials + JWT, `middleware.ts` ป้องกัน route ที่ต้อง login

#### 2.4.3 การอัปโหลดไฟล์

ใช้ **UploadThing** 3 endpoint:

- `profileImg` — รูปโปรไฟล์
- `inspectionImg` — รูปการตรวจแต่ละเกณฑ์
- `projectCoverImg` — รูปปกการ์ดโครงการ (เจ้าของเท่านั้น)

### 2.5 ระบบความร่วมมือหลายผู้ตรวจ (Collaboration)

1. เจ้าของโครงการเปิด collaboration จากเมนู share บน Project Card
2. ระบบสร้างลิงก์ `/join/[token]` ให้ copy ส่งให้เพื่อนร่วมทีม
3. ผู้ที่ได้รับเชิญ login แล้วกดลิงก์ → `POST /api/join/[token]` → เพิ่มใน `members[]` role `editor`
4. Editor แก้ไขเกณฑ์ได้ แต่ไม่ลบโครงการหรือจัดการ share
5. การ PATCH criterion ใช้ `expectedUpdatedAt` ตรวจ conflict — หากมีคนอื่นบันทึกก่อน คืน **409** ให้ refresh

### 2.6 ขั้นตอนการทดสอบ

- รัน `npm run dev` ทดสอบ flow บน localhost:3000
- รัน `npm test` สำหรับ unit tests (project access, concurrency, profile)
- รัน `npm run validate` ก่อน merge
- ทดสอบ OTP email (Gmail App Password) ใน `.env`

#### 3.1.1 ระบบบัญชีผู้ใช้

ผู้ใช้สามารถลงทะเบียน ยืนยันอีเมลด้วย OTP เข้าสู่ระบบ และจัดการโปรไฟล์ (รวมอัปโหลดรูปโปรไฟล์) ได้

> **รูปที่ 4** หน้าเข้าสู่ระบบ (Login)  
> **รูปที่ 5** หน้าโปรไฟล์ผู้ใช้

#### 3.1.2 แดชบอร์ดโครงการตรวจ

หลัง login ผู้ใช้เห็นรายการโครงการของตนและโครงการที่ถูก share พร้อมค้นหาตามชื่อและที่อยู่ แสดงสถิติโครงการที่เสร็จ/กำลังดำเนินการ และ progress รวม

> **รูปที่ 6** แดชบอร์ด All Projects พร้อมช่องค้นหา  
> **รูปที่ 7** การ์ดโครงการ (ปก, ความคืบหน้า, เมนู share)

#### 3.1.3 การสร้างโครงการและเลือกเกณฑ์

ผู้ใช้สร้างโครงการใหม่ ระบุชื่อ ที่อยู่/สถ institution และเลือกกลุ่มเกณฑ์จากมาตรฐาน 8 หมวด ระบบสร้าง sections และ criteria อัตโนมัติ

> **รูปที่ 10** รายการเกณฑ์พร้อมคะแนนและหมายเหตุ

### 3.3 ปัญหาที่พบ

1. **การแก้ไขพร้อมกัน** — เมื่อผู้ตรวจสองคนแก้เกณฑ์เดียวกันพร้อมกัน อาจเกิด conflict; ระบบคืน 409 แต่ยังไม่มี real-time sync
2. **OTP email** — การส่งอีเมลต้องตั้งค่า SMTP (Gmail App Password) ให้ถูกต้อง มิฉะนั้น register flow ล้มเหลว
3. **ขนาดมาตรฐาน** — ข้อกำหนด มยผ. 6301 มีจำนวนมาก การโหลดครั้งแรกบนเครือข่ายช้าอาจใช้เวลานาน
4. **Legacy API path** — path `critiria` (สะกดผิด) ถูกใช้ใน production ต้องรักษา backward compatibility

## 4. สรุปผลการดำเนินงาน

โปรแกรมประยุกต์บนเว็บสำหรับการตรวจสอบการออกแบบอาคารเพื่อการเข้าถึง สามารถช่วยผู้ตรวจบันทึกผลตามมาตรฐาน **มยผ. 6301** ในรูปแบบดิจิทัล ลดการพึ่งพาเอกสารกระดาษ และรวมข้อความเกณฑ์ ภาพอ้างอิง คะแนน หมายเหตุ และภาพถ่ายไว้ในแพลตฟอร์มเดียว ระบบรองรับการทำงานเป็นทีมผ่านลิงก์เชิญ และแสดงความคืบหน้าของแต่ละโครงการอย่างชัดเจน

ข้อจำกัดที่ยังพบ ได้แก่ การไม่มีการ sync แบบ real-time ระหว่างผู้ตรวจ การพึ่งพาบริการ cloud (MongoDB Atlas, UploadThing) และการประเมินความพึงพอใจที่ต้องเก็บจากกลุ่มผู้ใช้จริงเพิ่มเติม

**ข้อเสนอแนะในอนาคต**

- ส่งออกรายงาน PDF/Excel จากผลการตรวจ
- แจ้งเตือนเมื่อโครงการใกล้ครบหรือมี conflict
- เชื่อมต่อกับ ML service สำหรับวิเคราะห์ความเสี่ยงอาคาร (โฟลเดอร์ `ml-service/` มี prototype Random Forest)
- รองรับ offline mode สำหรับพื้นที่สัญญาณอ่อน
